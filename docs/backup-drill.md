# 备份与恢复演练记录

- **目的**：验证 P5-4「定时备份产出可用文件，且能从备份恢复出数据一致的库」

## 备份机制

| 项 | 值 |
|---|---|
| 方式 | `sqlite3 "$DB" "VACUUM INTO '$OUT'"` |
| 频率 | systemd timer，每天 04:00（随机延迟 5 分钟，`Persistent=true` 补跑停机期间的遗漏） |
| 产物 | `~/qqbot/backups/qqbot-YYYYmmdd-HHMMSS.db` |
| 保留 | 最新 14 份 |
| 自检 | 备份后立即 `PRAGMA integrity_check` + 统计行数；不通过则删除产物并以非零码退出 |

**为什么不用 `cp`**：数据库跑在 WAL 模式下，直接复制主库文件会漏掉 `-wal` 中尚未 checkpoint 的事务，得到一个「能打开但缺数据」的假备份。`VACUUM INTO` 由 SQLite 保证事务一致，且不需要停服。

| 1 | 向现网库插入一条标记数据 | 行数 0 → 1 |

## 结论

1. **备份是真实的时间点快照**：A 与 B 内容不同（0 行 vs 1 行），排除了「备份只是当前状态的拷贝」这一假象。
2. **恢复产物可用**：恢复后的库 `integrity_check` 通过，且服务能正常打开并连上网关。
3. **演练在库为空时进行**，对真实数据零风险。

## 未覆盖的部分（如实记录）

- **异地/离机备份未做**：备份与数据库在同一块 NVMe 上，磁盘损坏会同时丢失两者。若要防止这一点，需要把备份同步到别的机器或对象存储。
- **未演练「备份文件本身损坏」的场景**：`integrity_check` 自检能拦住大部分情况，但没有做注入损坏的测试。
